# 全量宏观数据有效更新审计

## 为什么旧普查会漏

- `data:verify-catalog -- --db` 能发现调度准入缺失，但不在日常 cron 中；它打印 `stale` 数量却不把这类状态作为失败项。
- `lagAlerts` 只读取前 500 条启用订阅，生产实际超过 6,000 条；`DATA_LAG_ALERT_AFTER_WORKER` 和邮件/Webhook 在香港机均未配置。
- `verify-labor -- --db` 的月频阈值是当前月减三个月，只证明有近期历史，不证明最新发布期入库。
- `DataSubscription.lastObsDate` 可能为空而 `MacroObservation` 已有导入历史；反过来，“抓取成功”也可能只取到源端上一期。
- 单次 worker 按发布包展开。香港生产 `cn.safe.bop-quarterly` 有 1,686 个成员，`cn.safe.iip-quarterly` 有 776 个成员；2026-10-03 曾有一轮处理 3,002 条、耗时超过四小时。定时 `flock` 会跳过这期间的其他轮次。

## 每日检查

`npm run data:audit-freshness -- --live-fred --strict --json=.data/audits/macro-latest.json`

GitHub Actions `Audit macro data freshness` 每天北京时间 10:15 独立 SSH 到香港运行：先审计、再限量自动回补有 FRED 源端证据的落后序列、最后重新审计。`--strict` 遇到剩余关键失败或 worker/日历无近期完成记录会使工作流失败。完整逐条结果保存在香港 cron 检出的 `.data/audits/`；Actions 日志输出分类计数、最严重的数据源/发布包和前 30 条示例。可用 `workflow_dispatch` 手工运行。

对已用实时 FRED 数据证明本地落后的序列，可运行 `npm run data:repair-fred-freshness -- --report=.data/audits/macro-latest.json --apply`。默认只预览、每次最多 50 条；仅处理近 366 天的源端最新期，使用统一 writer，且保留同包其他成员的排期。修复后重跑审计验证，不把“已发起抓取”当作修复成功。

检查范围：所有未标记目录 tombstone 的 `MACRO_SERIES`。检查事实为：

1. 有启用订阅，并且符合 **worker 实际使用** 的获取方式准入条件。
2. 观测表有数据；订阅 `lastObsDate` 与观测表末期一致。两者不一致单列为“状态漂移”，不能误报为空库。
3. 最近错误、从未成功抓取、到期仍未推进、worker/日历最后完成时间。
4. FRED 自动订阅与 **FRED 实时 API** 逐条比较末期日期，原始值序列还比较末期值，发现本地落后与源端修订。

非 FRED 指标现在只完成内部全量检查，报告中的 `sourceUnchecked` 明示尚未做逐条源端比较。不能把它们表述为“已验证有效更新”。后续应按源连接器增加同等的源端末期比较；对发布节奏特殊的指标维护有证据的例外，而不是用统一“近 90 天”阈值强行判断年频/季频。

## 2026-10-03 香港生产基线

首次只读实跑：6,421 条宏观指标、31 条目录隐藏历史存量、6,390 条可见指标；**755 个关键发现（可在同一序列上重叠）**，其中 539 条保留抓取错误、112 条无实际观测、48 条不能被 worker 选中、52 条超过频率宽限仍未推进。另有 1,081 条订阅末期与观测表不一致，多数是历史导入后从未写回订阅状态，不能算作缺数据。需按发布包汇总排障；`cn.nbs.real-estate` 的一个成员失败传播到数百个同包成员，不应人工逐条修 463 次。

首次 FRED 源端核对发现 21 条末期落后和 8 条同期期末值不同，去重后定向回补 28 条，重检时上述 28 条全部对齐；剩余 `IEASAD` 是源端止于 2019 年、本地无观测的历史序列，不能靠反复补抓当期数据解决。重检时仍有 757 个关键发现（含 539 条抓取错误），全站健康状态尚未达标。

优先处理顺序：

1. 无数据且不可调度的源：核对源端是否真的存在；对停更/不存在的世界银行序列标注 pending 或退出目录，不能只手动写 `known`。
2. 一个失败成员使整包失败的中国统计局房地产、CPI/PMI，先修根因和代理连通性，再重跑整包。
3. 将大包和普通宏观订阅分队列运行。`data:worker -- --source=<id>` 与 `--exclude-source=<id>` 已在查询前过滤，可作为分队列的安全基础；调整生产 cron 前须同时处理部署同步锁与包级执行时间。
4. 对非 FRED 连接器逐步补全源端末期核对和明确的预期发布滞后。

检查脚本不自动改写指标、删数据或把抓取失败伪装成“源端尚未公布”。
