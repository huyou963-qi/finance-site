# ZPAY 会员支付接入

## 范围与上线状态

新增 ZPAY API 订单的自动开通，复用 `PaymentOrder`、`User.plan/planExpiresAt`、`CreditLedgerEntry`、后台权限与审计。支持月费 39 元/30 天、年费 421 元/365 天、积分包 19 元/10 次；均为按次购买，不自动扣款。价格和权益以创建时的订单快照为准。

默认关闭。通用商户收款码不携带本站订单，不能用于自动开通。支付使用 ZPAY 官方 `submit.php` 收银台：本站后端生成带签名的订单字段，用户主动通过 POST 表单前往付款。私钥不发给浏览器。没有直接部署或启用真实收款，也没有真实资金联调记录。

协议接口依据：[ZPAY 开发文档](https://api.z-pay.cn/doc.html)，核对日期 2026-11-01。支持渠道由审核结果决定，不能把已有收款码视为 API 通道已审核。

## 迁移与配置

先部署迁移 `20261101090000_zpay_membership`，然后启动新应用；迁移仅给现有订单新增可空字段、索引和事件表，不改旧订单或旧权益。

```bash
npm run db:migrate
```

服务端 `.env.local` / 密钥管理配置：

```dotenv
APP_BASE_URL=https://gekkotech.cn
ZPAY_ENABLED=false
ZPAY_PID=实际商户ID
ZPAY_KEY=实际商户密钥
ZPAY_METHODS=alipay
BILLING_ALLOWED_ORIGINS=https://gekkotech.cn,https://www.gekkotech.cn
```

只有审核通过且准备验收的通道才能列在 `ZPAY_METHODS`。微信填 `wxpay`，双渠道 `alipay,wxpay`。`APP_BASE_URL` 必须是公开 HTTPS origin（不含路径、查询参数、用户名密码）；本地开发允许 localhost HTTP。不能从来访请求 Host 推导支付通知域名。

- 回调：`https://gekkotech.cn/api/billing/zpay/notify`，GET。
- 付款返回：`https://gekkotech.cn/pricing`，只显示状态，不以返回参数开通。
- 网关固定为 `https://zpayz.cn`，查单禁止重定向，单次超时 3 秒，响应上限 16 KiB。
- 必须配置公开回调地址可直达，不能加登录墙、验证码或把回调缓存。Nginx/CDN **不要记录 notify 的完整 query string**，其中含签名和订单信息；查单 URL 含密钥，应用从不打印 URL/原始异常。
- 更换 PID 时，旧订单不能用新商户凭据核验；需先清理旧待处理款项并安排旧商户收尾，不可直接替换后认为旧订单仍能补查。
- 仅关闭 `ZPAY_ENABLED` 会停止新结账；已有订单的通知和查单仍继续工作。不要因临时停卖删除 PID/KEY。

## 支付与权益一致性

1. 登录用户、同源 POST、服务端商品白名单和已启用通道，服务端定价。不接受浏览器指定金额、用户 ID、会员时长或交易成功状态。
2. 请求幂等键按用户唯一。相同键不同商品/方式拒绝；同用户同商品/方式已有未过期订单时，独立新键拒绝下单，界面按已有订单 ID 恢复付款，不混用幂等键。每用户每小时最多新建 10 笔在线订单。在线单号为 31 位数字，安全随机来源；本站付款入口展示 30 分钟；ZPAY 文档未提供此流程的有效关单接口，不能保证已打开或保存的收银台链接同步失效，已查实的迟到付款仍按原订单快照处理。
3. 回调严格拒绝重复参数、超长字段、错误签名、非本商户、错误金额/通道。未验签数据不入业务审计库，避免匿名灌日志；已验签金额等异常按订单/错误去重留痕。
4. 回调只是提示：必须服务端再向 ZPAY 查单，确认商户号、本站订单号、通道、金额、平台交易号和已支付状态。交易号全库唯一；大整数 ID 解析保留精度，金额按分精确比较。
5. 权益发放、订单已支付、唯一平台流水、发放时间和权益前后证据放在同一 PostgreSQL Serializable 事务。可重试的写冲突有限重试；失败整体回滚。重复回调、并发用户查单/cron 不重复续期或加积分。
6. 续费在有效到期日后叠加；首次购买保留尚未用完的试用天数。永久 Pro 不接受新的会员购买，既有合法付款不会把永久权益变为有限期。人工订单也复用同一权益发放实现。
7. 本地过期不能证明未扣款。查实已付的过期订单仍开通并标记 late；用户请先核验已有扣款订单，不要重复购买。
8. 停用/关闭账号收到真实付款时，记录到账流水、时间并置 `review`，不恢复账号权限或擅自开通；恢复 active 后可重新平台查单完成权益。永久关闭账号需管理员按售后处理，不能删除付款证据。
9. ZPAY 单不允许后台手工“确认收款”绕过查单。平台查单只依赖经验证的网关结果；管理员手工转账确认仍要求原有密码、TOTP、原因及审计。

## 跟踪、补查与资源预算

`payment_event` 是订单生命周期证据：创建、核验未付款/失败、异常通知、账号待处理、权益发放等。权益发放包含套餐到期时间/积分前后值、平台流水、是否迟到。不存商户密钥、原始签名、付款人账户或整个网关响应。

后台 `/admin/orders` 在桌面表格、手机卡片均提供“支付跟踪”和“平台查单”，最多取最近 100 条事件；订单列表最多 200 条。普通用户接口强制订单归属。后台权限沿用 `orders:write`（最高管理员/订单岗位及其现有 MFA）。

前端每 5 秒读本站状态，至多 10 分钟；隐藏页面不轮询，每约 30 秒可触发一次网关核验，数据库时间戳跨进程限制查询。付款信息在本标签页保存订单 ID，刷新可恢复状态；历史订单提供继续付款/核验入口。

后台漏单补查：

```bash
npm run billing:reconcile
npm run billing:reconcile -- --limit=25
```

生产部署会安装 `scripts/ops/finance-site-billing.cron` 与对应 logrotate；每分钟最多 20 单，先拿 billing 锁再解析工作目录，部署覆盖共享代码前也持同一锁。手动等价命令：

```cron
* * * * * root flock -n /tmp/finance-billing.lock sh -c 'cd /opt/finance-site && timeout 100s npm run billing:reconcile -- --limit=20' >> /var/log/finance-site-billing.log 2>&1
```

需确认 cron 用户可访问应用、环境文件和锁路径；为 `finance-site-billing.log` 配 logrotate，例如每日轮转保留 14 天、压缩并限制单文件 10 MiB。复用现有 Node/PostgreSQL，无新常驻进程。每轮最多 25 笔（上限 100）串行查询，单笔外部请求 3 秒；DB 使用现有池，外部等待不占事务，事务最大 5 秒。批查询走 `(channel,next_check_at)` 索引，内存随批大小增长。

失败从 1 分钟退避到最多 1 小时，自动补查窗口 7 天。超过窗口保留订单和事件、停止自动查询；用户/管理员仍可显式核验，迟到的有效回调仍处理。异常账号的已收款单每小时重查，最多 7 天；错误身份/金额/流水进入 review 并停止后台自动尝试，需处理。管理员应日常检查 `review`、有错误码及长时间未完成订单；当前没有新增邮件/短信告警。

日志增长预算：按每月 1,000 订单、每单 10–200 条事件估计约 10–200 MiB/月（含索引及 Postgres 开销，实际以 `pg_total_relation_size` 监测）。连续未付款会随退避产生更多事件；7 天窗口有界，重复已支付通知不重复写事件。订单及审计不自动删除；实际放量前按月度订单和事件密度验证磁盘预算。

## 验证

```bash
npx tsx --test src/lib/billing/zpay.test.ts
npm run test:billing-integration
npm run verify:commit
```

集成测试只允许 loopback PostgreSQL，使用临时数据库重建旧结构，再实际执行本次 SQL migration；模拟网关响应，不访问真实支付接口，不改应用业务库。测试涵盖登录、订单隔离、同源校验、通道关闭、并发下单、签名/金额篡改、必须查单、重复回调、并发月年续费、积分重复发放、唯一流水失败回滚、迟到付款、停用账号留款及恢复、网关故障退避、漏单恢复、永久 Pro 和人工确认防绕过。CI 有独立 PostgreSQL 17 集成测试 job。

真实验收必须等待审核并使用平台允许的真实交易：电脑支付宝扫码、手机支付宝唤起；开微信时再测手机微信内/外浏览器与电脑扫码。确认回调可达、订单 paid 且 fulfilledAt 非空、用户权益正确、后台证据完整。重复通知和再次核验不得再次加权益。真实联调不能以测试数据库的模拟网关结果替代。

## 当前边界与退款

没有实现退款扣款 API、自动续费代扣或微信 H5 专用能力；由 ZPAY 收银台及已获批通道决定具体付款体验。默认没有自动发起任何退款。

ZPAY 公布的查单接口没有在本次核对资料中提供完整退款状态/退款通知契约，因此不能可靠自动同步在其后台单独发起的退款。退款先核实原交易及可退金额，通过平台售后办理，并使用现有后台会员/积分调整流程（密码+TOTP+原因+审计）处理权益；财务退款记录以平台退款流水为准。不要直接在平台退完款后假设本站会自动撤销已发放权益。未来自动退款需新增退款状态机、网关不确定结果处理和独立可逆权益账本后再上线。

## 生产检查与域名

`npm run billing:check -- --gateway` 只读验证配置、迁移字段与网关认证，只报告布尔结果，不输出 PID、KEY、余额或用户信息。`ZPAY_ENABLED=false` 不影响此检查。本站 www 与非 www 均返回页面时，需用 `BILLING_ALLOWED_ORIGINS` 明确配置允许来源，拒绝 HTTP、通配符和附带路径/认证信息的来源。

回调 Nginx snippet 为 `scripts/ops/finance-site-zpay-notify.conf`，部署会安装至 `/etc/nginx/snippets/`；首次需在 HTTPS server 中加入 `include /etc/nginx/snippets/finance-site-zpay-notify.conf;`，备份现有站点配置、通过 `nginx -t` 后 reload。回调访问日志关闭，不影响业务支付事件审计。

`npm run billing:smoke -- --create-unpaid-probe` 是需显式启用的运维探测，只创建一笔39元未付款网关订单，保留部署探测事件，随后关闭测试账号并停止该订单自动补查，不付款、不充值、不退款、不发放会员；不能替代真实付款验收。只能从生产SSH会话运行（使用服务器来源IP）。收银台返回已验证的下单来源域名，避免跨www别名丢失登录态。
