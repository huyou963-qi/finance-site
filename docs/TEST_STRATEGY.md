# Finance Site 测试策略与提交门禁

## 1. 目标

测试门禁要同时防止四类事故：页面打不开、权限被绕过、金融计算/数据口径悄悄变化、数据库与部署产物不一致。任何分支 push 和面向 `main` 的 PR 都必须通过同一个 `CI / build` 检查；生产部署仍只由 `main` 触发。

测试遵循“代码与确定性夹具是事实源”的原则。提交门禁不连接生产数据库、不依赖真实密钥、不向第三方写数据；FRED、FMP、Yahoo、SEC、国家统计局等外部源使用固定夹具或 mock。真实源连通性和数据新鲜度属于定时验证，不应让普通提交因网络波动随机失败。

## 2. 分层与执行频率

| 层级 | 命令/触发 | 内容 | 目标时长 | 是否阻断合并 |
|---|---|---|---:|---|
| L0 开发反馈 | `npm run test:unit --` 或原有模块命令 | 纯函数、解析器、金融计算 | 2 分钟内 | 是 |
| L1 快速门禁 | `npm run verify:quick` | 全部单元测试、架构守卫、Prisma validate、lint | 5 分钟内 | 是 |
| L2 提交门禁 | `npm run verify:commit` | L1 + Next.js 生产构建/类型检查 | 10 分钟内 | 是 |
| L3 集成/E2E | PR 或测试环境（待接入） | PostgreSQL migration、API、浏览器关键旅程 | 15 分钟内 | 核心用例是 |
| L4 数据/运行质量 | 定时任务、部署后 | 外部源契约、新鲜度、性能、安全扫描、线上 smoke | 独立运行 | 告警；严重项阻断发布 |

当前已落地 L0–L2。测试运行器会递归发现 `src/**/*.{test,spec}.{ts,tsx}` 和 `tests/architecture/*`，新增测试无需再手工修改 `package.json`。

## 3. 每次提交的固定门禁

`npm run verify:commit` 按以下顺序执行：

1. 运行现有全部业务单元测试与架构守卫。
2. `prisma validate` 检查 schema 语法、关联和生成配置。
3. ESLint 检查 React/Next.js/TypeScript 规则。
4. `next build` 完成生产编译、类型检查、服务端/客户端边界检查和路由生成。

CI 对所有分支 push 执行同一流程。GitHub `main` 分支保护必须要求 `CI / build` 成功，且禁止管理员绕过。生产部署 workflow 会在打包和连接服务器前再次执行 `verify:commit`，因此 CI 与部署并行触发时也不会绕过门禁。开发者本机失败时不要用跳过 hook/CI 的方式提交，应修复或在 PR 中说明经负责人批准的临时隔离方案。

## 4. 已自动化的核心范围

### 数据与金融计算

- K 线前复权、后复权、拆股与分红因子、价格边界。
- 行业收益、历史行业分类、ETF 持仓、阶段归因与传导。
- SEC 财报季度化、基本面聚合、比率、首次披露时间与 vintage。
- 量化因子、回测、稳健性、宏观 Regime、13F 与资金因子。
- 宏观 observation vintage、频率、序列变换、目录树和布局映射。
- 中国官方数据、ISM、CFTC 等解析器的固定输入夹具。

### 架构与安全守卫

- `"use client"` 文件不得读取非 `NEXT_PUBLIC_*` 环境变量。
- 所有 `/api/admin/**` Route Handler 必须调用 `requireAdmin()`。
- 直接渲染 `useSearchParams()` 客户端组件的页面必须有 `Suspense`。
- 生产源码不得包含私钥块。

这些守卫是最低线，不替代对登录态、对象所有权、限流和输入校验的行为测试。

## 5. 功能测试矩阵

下面每个 P0 用例最终都应成为自动化测试。新增功能必须在同一 PR 中更新对应模块测试；修复 bug 时先添加能复现 bug 的回归用例。

| 模块 | P0：每次 PR 必测 | P1：每日/发布前 | 主要断言 |
|---|---|---|---|
| 首页/导航/主题 | 首页、主导航、错误页可渲染 | 手机/桌面截图比较、键盘导航 | 无 5xx、无 hydration error、焦点可见 |
| 注册/登录/账号 | 注册校验、登录成功/失败、退出、`/api/auth/me` | 邮件验证、session 过期/撤销、并发登录 | Cookie 安全属性；401/403 正确；密码不回传 |
| 订阅/订单 | 免费/Pro 权限、订单所有权、管理员处理 | 支付回调幂等（接入支付后） | 普通用户不能读改他人订单；重复请求不重复记账 |
| 宏观仪表盘 | 目录加载、模板加载、序列查询、图表变换 | 大模板、导出、跨页同步、空数据 | 单位/频率/日期/as-of 正确；无未来数据泄漏 |
| 宏观偏好 | 未登录 401；用户 CRUD；系统模板管理员权限 | 冲突更新与大 JSON | 用户隔离；非法结构 400；系统模板不可越权 |
| K 线行情 | AAPL 日线、无效 symbol、interval/adjust 校验 | 周线聚合、盘中线、缺口回补 | OHLC 合法；排序去重；复权结果与金标准一致 |
| 股票搜索 | 代码/公司名、大小写、特殊代码 | 全量 SEC 数据性能 | 相关性稳定；无 SQL 注入；响应上限 |
| 行业/公司详情 | 行业列表、成分、收益、基本面、同行 | 历史分类切换与 delisting | 截面日期一致；权重之和合理；禁止 hindsight |
| 因子/筛选/回测 | 参数边界、结果确定性、Pro 门禁 | 大股票池、长周期、稳健性组合 | PIT 数据；交易日对齐；费用/换手/回撤计算正确 |
| Regime | 当前状态、历史阶段、forward study | 月度结算与 live ledger | 信号只用当时可见数据；到期前不提前评分 |
| 事件时间线 | 公共读、管理员写、过滤、图表 marker | 图片附件、批量 ingest、重复导入 | 权限/所有权；幂等；日期区间和优先级正确 |
| 投资案例 | 新建、编辑、研究、催化剂、交易计划、导出 | 多用户并发和大附件 | 用户隔离；状态机合法；导出不泄露内部字段 |
| 周报 | 列表/详情、ingest token、删除权限 | Markdown/图片兼容与分页 | token 错误拒绝；HTML 安全；重复发布幂等 |
| 管理端 | 所有 API 匿名/普通用户拒绝，admin 成功 | 审计日志、批量操作 | 写操作有鉴权、校验、审计；错误不泄密 |
| 数据调度 | seed 幂等、release package、日历 fan-out、writer | 外部源契约、新鲜度/滞后告警、重试 | 单一 writer；nextRunAt 正确；失败可重跑不重写事实 |
| Migration/部署 | schema validate、build、包内容 | 空库全量 migrate、上一版库升级、回滚演练 | migration 不改写；部署包完整；启动 health check 通过 |

## 6. 下一阶段应补的自动化套件

### 6.1 PostgreSQL 集成测试（优先级 P0）

在 CI service container 启动与生产同大版本 PostgreSQL，使用专用 `finance_site_test` 数据库：

- 从空库执行 `prisma migrate deploy`，再运行最小 seed。
- 从上一发布版本 schema 快照升级，验证数据保留。
- 对用户、session、偏好、订单、事件、投资案例执行真实事务测试。
- 对 `mds` observation/vintage、价格、拆股、分红、财报执行唯一键与幂等测试。
- 每个 test file 使用事务回滚或独立 schema，禁止共享可变顺序状态。

### 6.2 API 契约测试（优先级 P0）

为每个 Route Handler 建立表驱动用例，至少覆盖：合法请求、缺参/非法参、匿名、普通用户、Pro、admin、上游超时、数据库错误。响应需断言 HTTP 状态、稳定 JSON 字段、分页边界、错误信息不包含 SQL/堆栈/密钥。OpenAPI 尚未引入前，可用 TypeScript fixture 作为契约金标准。

### 6.3 Playwright 浏览器旅程（优先级 P0）

使用隔离测试库和固定账号运行以下最小 smoke：

1. 匿名访问首页，进入宏观页并加载固定序列。
2. 搜索 AAPL，打开 K 线，切换复权与周期，确认图表无控制台错误。
3. 登录免费账号，保存宏观模板并刷新恢复。
4. Pro 账号运行一个最小筛选/回测并查看结果。
5. 普通用户访问 admin 返回无权限；admin 可查看但不在 smoke 中执行破坏性批量操作。
6. 手机视口打开首页、宏观、行情、定价页，无水平溢出和遮挡。

失败时保存 screenshot、trace、console 和 network 日志；禁止仅靠文字选择器定位易变 UI，优先使用 role/label 和稳定 `data-testid`。

### 6.4 性能与容量（优先级 P1）

测试环境用脱敏的规模化数据执行 k6/等价工具：

- 首页/静态页 p95 < 1 秒；缓存命中 API p95 < 500ms。
- K 线与宏观查询 p95 < 1.5 秒，单响应体设明确上限。
- 目标并发按 50 → 200 → 1000 阶梯压测，记录吞吐、错误率、DB 连接、CPU、内存。
- 登录、搜索、回测创建分别限流验证；慢查询进入 explain 基线。

阈值需用真实部署规格校准后固化，不能用本机偶然结果直接作为生产 SLO。

### 6.5 安全与韧性（优先级 P1）

- 依赖漏洞与 secret scanning；高危漏洞阻断发布。
- CSRF、XSS、SQL 注入、路径穿越、超大 body、图片类型伪造。
- IDOR：替换 userId/orderId/investmentId 不得访问他人数据。
- 外部源 429/5xx/超时/畸形数据时，重试有上限并保留最后可信数据。
- 数据库不可用、邮件失败、上游失败时页面降级且不暴露内部信息。

## 7. 测试数据规范

- 时间统一为 UTC，夹具明确记录 source time zone、release time 和 as-of time。
- 金融金标准包含拆股、现金分红、月末、闰年、节假日、停牌、退市、负值和空值。
- 个人数据全部虚构；严禁复制生产用户、session、token、邮件或密钥。
- 外部响应 fixture 保存来源接口、抓取日期和最小必要字段；接口变化时人工审查后更新。
- 快照只用于稳定结构或视觉，不用大快照掩盖金融数值断言。

## 8. 失败处理与责任

门禁失败先判断是产品缺陷、测试缺陷还是不稳定外部依赖。产品缺陷必须修复；测试缺陷需在同一 PR 修复并说明；外部依赖应改成 fixture/mock。不得简单重跑直到变绿。确需隔离 flaky 测试时，创建有负责人和截止日期的 Issue，测试仍在每日任务运行并发出告警。

发布后的首页、鉴权接口和关键只读 API smoke 失败时应停止继续发布并恢复上一可用版本；涉及金融口径或权限泄漏的事故按最高优先级处理。

## 9. 新功能完成定义

- 纯业务逻辑有单元测试，关键错误分支和边界值有断言。
- 新/改 API 有权限矩阵和输入契约测试。
- UI 关键旅程有浏览器测试或 PR 中记录的人工验证，且无控制台错误。
- 数据功能说明复用了哪些 adapter、canonical store、writer 和计算服务。
- schema 变更带新 migration，并通过空库与升级测试；不修改旧 migration。
- `npm run verify:commit` 通过，PR 模板中的测试与部署项填写完整。
