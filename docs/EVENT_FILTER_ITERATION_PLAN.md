# 事件筛选与用户事件闭环优化方案

日期：2026-10-28。状态：第 1、2 轮已在本地实现与验证，详见 [第 1 轮记录](EVENT_FILTER_ROUND1.md)、[紧凑布局修订](EVENT_FILTER_COMPACT_REVISION.md)和[第 2 轮记录](EVENT_FILTER_ROUND2.md)；尚未部署。基于当前仓库代码检查，未验证生产页面或生产数据。

## 目标与现状

用户打开一个资产后，能快速回答：有哪些相关事件、为什么出现、为什么某条没有出现、如何把自己的专题放到 K 线上。

保留系统事件与用户事件的独立来源、独立筛选偏好，以及主图合并展示的基础。复用既有事件协议、资产解析、事件包与 writer，不新建平行事实库。

当前实现依据：

- `src/components/equity/MarketsEventShelf.tsx`：来源切换、筛选、包管理、样式和导入共处一个组件；导入会主动改变部分内容筛选和上图状态。
- `src/components/events/EventPanelFilters.tsx`：搜索、类型、公司细类、最低重要度、预期差、五种标签条件集中呈现；“仅大预期差”对非宏观事件也可操作。
- `src/lib/chart/eventViewFilters.ts`：内容条件、来源、隐藏记录、颜色和布局存在同一个状态结构中，系统偏好位于根字段，用户偏好嵌套保存。
- `src/lib/chart/eventSelection.ts`：两类分别筛选后去重合并；合并结果用于列表，因此用户注释可能使系统页对应事件不再出现。应保留来源列表，再单独合并主图投影。
- `src/lib/equity/useLocalCompanyEvents.ts`：用户包保存在按账号分区的 localStorage；当前机制不构成跨设备同步或外部 Skill 自动投递。按 externalId 合并还需检查跨包身份冲突。
- `src/lib/chart/useChartEvents.ts`：共享事件按范围加载后再统一选取；页面统计只能代表当前已加载集合，不能代表全部事实覆盖。

## 一、将操作分成三层

| 层次 | 用户问题 | 控件 | 操作影响 |
| --- | --- | --- | --- |
| 来源 | 从哪里看事件？ | 系统事件 / 用户事件；系统来源 / 用户事件包管理 | 决定候选集合 |
| 内容 | 我要找什么？ | 搜索、类型、重要度、关联范围、更多条件 | 决定本类列表及可上图候选 |
| 展示 | 如何放到图上？ | 本类上图、文字、颜色、单条上图 | 不改变列表内容 |

切换来源只切换管理视图，不开关另一来源；内容筛选只影响当前来源。主图继续合并两类已启用事件。

推荐默认界面：

```text
系统事件  /  用户事件                      来源管理
当前资产 AAPL · 跟随图表时间区间
搜索事件…    类型：全部    重要度：中及以上    更多筛选
已选条件：包含宏观关联 ×                      清除内容条件
符合条件 N 条 · 上图 M 条                     查看排除原因
事件列表 / 卡片 / 时间线                    图表显示设置
```

此处 N、M 为界面占位。实际统计必须来自同一批选取结果。

“来源管理”按页打开系统来源或用户事件包；“图表显示设置”收纳颜色和文字等低频操作。桌面默认仅展示一行常用筛选；手机保留来源切换、条件摘要和“筛选”按钮，条件放入底部面板，显示待应用数量，点击“应用”统一提交。两端提供相同功能与权限入口；手机控件避免现有密集的小字点击区域。

## 二、明确筛选规则

1. 同维度多选取并集，不同维度取交集。类型一个都未选代表零结果，明确提供“全部 / 清空”。空标签条件代表不限。
2. 资产关联控制候选范围；国家、人物、机构等控制内容收窄。界面区分“关联范围”和“内容标签”，不让用户误以为修改包展示范围就改写了事件资产标签。
3. 公司细类仅在公司类型选中时出现。“仅大预期差”放入宏观专属条件，说明它会排除其他类型以及缺少有效预期差证据的事件；不表示利多或利空。
4. 每个生效条件都有可删除的摘要。折叠高级面板后仍能看见生效条件数量与摘要。
5. 将重置拆成明确动作：“清除内容条件”保留来源、事件包、颜色和上图设置；系统页另有“恢复资产默认”。用户页不使用“标的默认”这种含糊文案。
6. 关闭“本类上图”后列表保留。单事件操作区分“隐藏此事件”和“仅从图上隐藏”，并提供可恢复入口。
7. 导入保留原有筛选，展示“已导入 X 条，其中 Y 条符合当前条件”；提供“查看本次导入”临时视图及退出入口。不得为了让结果出现而静默清除用户条件。
8. 系统页、用户页各自保留命中的来源记录；仅在主图投影时合并重复事实，详情可查看来源与私人注释。列表数量与主图数量可不同，明确标注重复合并数量。

## 三、让“没有事件”可以解释

由统一选取流程产生阶段统计与原因，而非界面另写一套判断：

```text
来源已加载 → 资产/包范围适用 → 图表时间区间内 → 内容匹配 → 来源列表
                                                       ↓
                                             合并事实 → 上图开关 → K 线对齐
```

各阶段记录实际输入与输出数量；若原因互斥计数，按固定顺序记录首个排除原因。单事件诊断可列出全部不满足条件，避免把多原因计数误加为总排除数。

空状态区分：来源关闭、包不适用、区间外、内容不匹配、加载失败、尚未导入。给出对应动作，例如“查看包范围”“清除类型条件”“重试加载”。加载失败不能展示成确定的零事件。

远端资产关联在服务端分页前执行，当前客户端无法解释未返回记录的排除原因；第一轮仅报告可观察阶段，并标“当前查询已加载”，后续按需补服务端诊断，不虚构完整覆盖率。

## 四、用户 Skill 到 K 线的闭环

需要分开建设“事件采集任务”和“页面筛选”。用户说“找过去三年影响黄金的地缘事件”，这是生成专题包的采集任务；页面搜索仅在已有事件中查找。

任务应保留：专题、资产范围、起止日期、事件类型、来源要求、更新方式、稳定任务 ID。Skill 输出沿用现有协议与稳定包 ID，事件保留原始证据、实际发生时间、时间精度和稳定 externalId。未知时刻不得填造精确时间。

分两阶段落地：

- 第一阶段继续文件导入：Skill 生成兼容事件包 → 校验 → 导入预览 → 幂等写入 → 展示本次新增、更新、未显示的原因。界面明确“保存在此浏览器”，支持备份导出。
- 第二阶段实现自动投递：复用站点账号认证与事件校验，建立用户私有包接收接口和存储；绑定账号与包权限、限制包大小、校验来源链接协议，按任务 ID / 包 ID / 事件 ID 幂等更新。Skill 获取投递回执，网页刷新私人包后自动显示符合条件的事件。先设计接口与权限，再承诺自动加载。

任务状态可展示“等待执行 / 采集中 / 校验失败 / 已保存 / 已同步”；是否上图单独展示，避免“同步成功”被误解为“当前 K 线一定可见”。持续更新需要有明确调度执行方，不能仅靠 Skill 文本宣称会自动运行。

身份需要区分包内更新键 `(packId, externalId)` 与跨来源事实关联键；不同专题相同 externalId 不应自动互相覆盖。跨来源事实去重继续保守处理，不按同一天同类型推定相同事件。

## 五、逐轮迭代与验收

每轮循环：选一个可复现问题 → 留下当前基线 → 做一个最小改动 → 跑固定任务与回归 → 记录结果 → 保留或回退 → 排下一轮。AI 可以提出下一轮问题和实现修复；事实采集规则、相关性与重要度调整需有样例依据，不因点击次数直接改写事实或共享规则。

| 轮次 | 交付 | 验收 |
| --- | --- | --- |
| 1：筛选变清楚 | 三层操作、常用条件收敛、生效摘要、明确重置、宏观条件归位 | 桌面和手机完成来源切换、按类型查找、清除条件、关闭上图；另一来源偏好保持；关闭上图后列表保留 |
| 2：解释和一致性 | 阶段统计、空状态原因、来源列表与主图投影分开 | 被筛掉的样例能解释原因；重复事实在两来源页仍可追溯；只有明确的合并或展示条件导致列表/图表差异 |
| 3：导入可靠 | 导入保留偏好、本次导入视图、更新差异、跨包身份处理 | 同包重导不重复；不同包同 ID 不误覆盖；事件不显示时能定位区间、包范围或条件原因 |
| 4：自动投递 | 私有包接口、认证、幂等回执、网页刷新与任务状态 | Skill 投递到正确账号；重复与失败重试不重复；其他账号不可读写；同步成功和可上图数量分别呈现 |

第一轮不做全面状态重构；在现有独立来源偏好上整理交互。后续确需拆分状态时，采用 `source / content / presentation` 职责分离，并保持旧 localStorage 的可回滚迁移，不因字段重排丢失已有设置。

固定任务集：

1. AAPL 查财报类系统事件，再切用户页，检查另一来源不被改变。
2. 黄金只看有有效证据的大预期差宏观发布，再恢复全部类型。
3. 用户包导入成功，但所有事件在当前图表区间外。
4. 两个包包含相同 externalId；同包另有一条事件修订。
5. 系统与用户包含同一事实，用户事件被筛掉或仅关闭上图。
6. 远端加载失败，本地包仍能查看。
7. 周末事件对齐下一交易日，详情保留原始日期。

第一轮先记录任务成功率、完成时间和误操作，不编造改进百分比。后续以相同任务比较；筛选正确性与私人包隔离属于必须通过的约束。每轮至少复核桌面和手机，并针对改动运行现有相关测试；代码交付执行项目要求的构建检查。

迭代记录模板：

```text
轮次 / 日期：
问题与复现步骤：
假设及本轮唯一主要改动：
基线 / 改后结果：
桌面 / 手机验证：
测试及未验证范围：
保留或回退及原因：
下一轮优先问题：
```

## 建议起点

先完成第 1 轮，把当前筛选器整理为用户能理解的操作层级；第 2 轮建立可解释的结果和统计。这样第 3、4 轮新增导入与自动同步时，可以直接说明每条事件是否进入当前图表，以及原因。
